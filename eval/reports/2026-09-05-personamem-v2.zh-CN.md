# PersonaMem-v2 首轮实测：尚未观察到稳定个性化收益

本次完成了真实的历史写入、跨窗口巩固、上下文投递和官方选择题评分，不是 mock 或接入 smoke test。结论是：**当前默认配置没有显示稳定收益；不能据此宣传优于 Mem0，也不能宣称人格／Seed 闭环有效。**

> 2026-09-08 解释修正：本轮四组共同获得了官方 system 中的完整 `expanded_persona`。因此下文的 `none` 是“完整用户画像已知、无额外长期记忆”，不是真正的无记忆基线；本报告保留历史结果，但不再用于判断自然长对话记忆是否有效。新的六组诊断与 OmniMemEval Adapter 都排除该生成侧画像。

## 结果

固定抽样 20 个用户，每人 5 题，共 100 题、400 次回答；四组使用相同模型、题目、选项、共同初始画像和预算。

| 模式 | 正确数／100 | 准确率 | 平均额外记忆 tokens | 非空记忆题数 | 官方格式无法解析 |
|---|---:|---:|---:|---:|---:|
| 无长期记忆 `none` | 39 | 39% | 0 | 0 | 2 |
| 原文 RAG `episode_rag` | 33 | 33% | 943.23 | 100 | 5 |
| `recollection_only` | 35 | 35% | 104.07 | 90 | 2 |
| 完整 Core `full_core` | 34 | 34% | 104.07 | 90 | 1 |

全部 400 次回答无 API 错误。无法按官方格式解析的回答照常计错，没有放宽评分规则。

按用户聚类的配对 bootstrap（2,000 次，seed=0）：

| 比较 | 准确率差值 | 95% 区间 |
|---|---:|---:|
| 完整 Core − 无记忆 | −5 个百分点 | [−13, +3] |
| 完整 Core − 原文 RAG | +1 个百分点 | [−7, +9] |

两个区间都包含零。这个 pilot 不足以断言 Core 更好，也不足以断言它必然更差。额外记忆上下文更短，但这不等于端到端成本更低：后台巩固成本必须计入。

## 实际测到了什么

- 2,324 个完整历史 Episode，93 个后台巩固窗口，全部完成，无待处理 Job。
- 形成 135 个 Recollection version，其中 129 个 active、6 个修订版本。
- 38 个 Recollection version 的依据来自多个输入批次，分布在 17 个用户中；其中 24 个版本的最早与最晚批次编号相差至少 2。
- 全部 20 个用户答题前后，记忆版本、Basis 和巩固 Job 保持不变。实验结束后再次与真实 MySQL 状态逐项比较，一致。

这些证据证明“历史跨窗口延续并形成可投递记忆”确实发生了，**不能单凭来源跨窗口就证明跨窗口推理或隐含偏好应用获得了收益**。本次没有做关闭跨窗口关联的独立消融。

本轮形成 **0 个 Disposition**。100 题的两个 Core 模式上下文逐字相同，却有 11 题正确性不同，因此 `full_core` 与 `recollection_only` 在这里应视为相同记忆输入的两次独立采样，而不是有效的 Disposition 消融。即使 temperature=0，模型服务也没有给出逐字确定性保证。

PersonaMem-v2 的目标是从长历史中的隐含偏好产生个性化回答，不等于评测 Agent 自身人格。测试阶段没有虚构外部 Outcome，也没有测行为后的反馈学习。[官方项目](https://github.com/bowen-upenn/PersonaMem-v2)、[论文](https://arxiv.org/abs/2512.06688)。

## 已定位的损耗

用本轮相同的 Go `consolidation.ParseTaggedText` 重放所有 Worker 输出，并逐项对照当次提供的 TARGET／BASIS：

| Worker 输出 | 窗口数 |
|---|---:|
| 语法与提供的引用均通过检查 | 69 |
| 主动返回 `NO_CHANGE` | 15 |
| 语法错误 | 6 |
| 引用不在当次允许集合 | 3 |

后两类共 9/93 个窗口会被 Core 的整批校验拒绝。4 个语法不完整的输出恰好达到 8,192 completion tokens 上限，符合截断现象；其余包括重复 Target、重复 Basis 和不完整的 Episode ID。这里的“通过”只指语法与引用检查，不把它等同于语义正确。

在线另有 10/100 题没有获得任何 Core 记忆。当前默认选择器是字符 bigram Dice，本轮未配置 MemoryIndex。这是明确的选择能力限制，不能当成已经验证过语义检索后的结果。

上述是实际观察到的损耗；尚未通过分别修复后重跑来量化各自对准确率的因果贡献。本轮不改 Core／Worker 提示词、不筛掉失败题，也不事后挑选表现较好的子类别。

## 成本与时延

模型服务返回的真实 token 用量：

| 阶段 | 调用数 | 输入 tokens | 输出 tokens |
|---|---:|---:|---:|
| 后台巩固，供两个 Core 模式共享 | 93 | 1,288,235 | 108,486 |
| 四组回答合计 | 400 | 686,472 | 76,903 |

不把共享的后台成本重复计入两个 Core 模式，也不把它隐去。未换算美元金额，以免混淆缓存、实际计费和模型价格变化。

- 完整 Core 客户端上下文准备：平均 45.67 ms，p95 82.27 ms；包含 Observe、Select、完整条目组装及必要的 Delivery，不是纯服务端 Select 压测。
- 完整 Core 单题总时延：平均 2,298.81 ms，p95 4,273.58 ms；包含上下文准备和回答生成。
- 后台 Worker 模型调用：平均 6,327.67 ms，p95 39,294.46 ms。

以上是本地单次顺序实验，不是并发 SLA。额外记忆预算使用 `cl100k_base` 计数，表中调用用量来自模型服务，两种计数口径不混用。

- 全部 400 个保存答案重新执行固定上游评分器，**0 项差异**；全部 20 份历史也已与固定 HF revision 的独立 Git blob 指纹核对。

本轮连续运行完成，没有使用中断恢复。审查之后修复了评测工具的两项问题：首题前原子保存原始记忆快照，恢复不得绕过比较；首次接纳历史缓存也必须核对上游指纹。旧 pilot 可凭其完成证明只读汇总，但不能用改版源码直接继续 `run`。这些修复没有改变本轮已保存的答案或评分。

**下一步建议只处理一个变量：先降低后台文本结果被整批拒绝的比例，再在独立开发用户上测试语义召回。** 当前这 20 个用户已经用于诊断，不应再充当调参后的唯一最终测试集。真正的 Disposition 反馈收益需另做有实际行为与外部结果的在线评测，本次不替它下结论。
