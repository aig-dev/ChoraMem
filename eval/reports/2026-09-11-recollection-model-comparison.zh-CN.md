# Recollection 固化模型对照：不支持直接切换 M2.7

**本轮六次调用已完成，两组均未通过严格来源门槛，不扩跑、不部署。** M2.7 在船长案例中重新叙述多项已撤回内容并混入第三方身份；M2.5 增加了原文未明确支持的年龄归因。与此同时，M2.5 的新鲜对照比上一轮明显完整：相同输入下的输出波动，不能被误算为换模型的收益。

## 冻结的范围

- 使用已批准的独立 Recollection 文本加工 Spike，不是生产统一 Worker，也不是公开 benchmark 成绩。
- 固定三个此前已选定的 focused 输入，每份含一段待加工原文及完整 28 组 USER／ASSISTANT 上下文；不读取问题、答案或隐藏 persona。
- 唯一请求变量为模型 ID：`MiniMax-M2.5` 与 `MiniMax-M2.7`。指令、输入、完整背景、参数、正文绑定和来源门槛不变。
- 两侧均调用原有 `ChatTextModel`：`https://api.minimaxi.com/v1`、temperature=0、reasoning_split=true、max_tokens=8192、timeout=110s、max_retries=0。没有对 MiniMax 发送关闭 thinking 的参数。
- 三个 case 的模型顺序为 M2.5→M2.7、M2.7→M2.5、M2.5→M2.7。每个模型每例只调用一次；不把过去的结果充当本轮对照。
- AI 只返回正文；程序仍绑定 `NEW_RECOLLECTION / OTHER / TEXT` 及整个窗口的 28 个 Episode refs。这里是窗口级来源关系，不是逐句最小证据。
- 门槛仍为至少 2/3 指定背景得到保留，且没有实质来源／撤回错误。正常返回和语法通过均不能替代语义门槛。

## 逐例结果

| 案例 | M2.5 | M2.7 |
|---|---|---|
| 929：外交工作、孩子、临时工作对家庭时间的挤压 | 保留主要背景，未保留已撤回的 daily planner | 保留主要背景，未保留 daily planner；正文更长 |
| 374：产品发布、青年志愿服务、精力不足 | 保留主要背景与当前 workshop 承诺 | 同样保留主要背景与当前 workshop 承诺 |
| 742：退休、膝痛、耐力、旅行与自我感 | 保留主要背景；增加了原文未明确给出的 `age-related` 原因性修饰 | 扩写成宽泛人物档案，把 botanical gardens、雨声、daily journal 等已要求遗忘的内容重新写入，还把第三方活动组织者写成用户身份 |

374 的撤回文本针对“喜欢通过 workshop 学习新技能”，不是明确撤回这一次已报名的具体承诺。本轮两个输出均未声称这一学习方式偏好；不把具体承诺自动判为偏好复活，也不借这一边界放过 742 的明确撤回错误。

742 的船长、数十年海上经历和 Cavite 在用户本人认领的回忆录／个人笔记中有支持，不能仅因它们不在 focused 段落中就误报为 Agent 捏造。不过来源有支持也不代表应该导入不相关资料；M2.7 明显超出了当前素材的加工范围。`history:21` 的待润色段落写的是第三方 Maria Elena Cruz 为 lead organizer，并没有说明这是用户本人；M2.7 却把 serving as lead organizer 加进了用户档案。标注某项内容“后来忘记／撤回”也没有消除对该内容的重复保存。

独立语义复核已完成：929／374 的两模型结果均通过；742 的两模型结果均未通过。M2.5 的 `age-related` 比“身体正在变化”的直接自述更强，给健康限制增加了未明确支持的原因，因此这里按实质来源错误记录。若将它视为非实质性的概括措辞，M2.5 的门槛判定会改变；这是本轮真正的判断边界，不影响 M2.7 的明确失败。

**门槛结果：M2.5 主要背景覆盖 3/3，但有一例来源归因错误；M2.7 有两例合格，一例存在多项来源／撤回错误。两组均未满足零实质错误要求。** 这里只报告三段背景的保留情况，不报告“三题答题准确率”，也不据此断言两种模型普遍不能处理长期记忆。

## 同模型前后波动

三个新 M2.5 请求与上一轮 `focused` 请求逐字段相同，包括 request hash、指令、实际输入、模型配置和来源列表；使用的客户端代码摘要也相同。三份正文却全部发生变化：929 从原文回显变成简短摘要，374 从 `NO_MEMORY` 变成背景摘要，742 更完整地保留了自我感担忧。

因此，上一轮“不稳定”仍有证据，但“只因 M2.5 能力不足”没有得到这次对照支持。不能仅凭一次失败否定一种流程，也不能凭一次成功宣称流程已经稳定；本试验没有进一步识别服务端为何产生这种差异。

## 后续只读核查：小样本门槛与通用执行边界

上述严格门槛与原始结果保持不变。但“未通过三例零错误检查”不是“没有端到端收益”的证据；尤其不能把 M2.5 的一处原因性修饰，外推成整个文本加工方向不可用。另一方面，人工预选材料后得到的摘要也不能直接作为通用固化框架的成绩。

本轮沿现有接口确认了两个尚未解决的工程前提：

- `.cache/recollection-focused-v1/probe.py` 的 `FOCI` 写死三个 persona 的来源位置，`records_for` 依赖这些冻结案例的具体外层布局。它没有任意聊天的自动材料遍历，也没有已有 Recollection 的通用修订／去重流程。
- `api/memory/inference/v1/inference.proto` 目前只有 `window_text` 和允许使用的 refs，没有机器可读取的 Episode／Source 边界。两种数据库的 `renderConsolidationWindow` 均将原文直接接在 `SOURCE` 行后。按该格式构造的纯字符串反例已确认：把含完整 `SITUATION / ACTOR / SOURCE` 行的片段从 Agent 正文移至 User 正文，可以得到完全相同的窗口文本和 Episode refs。这个反例未调用 Go renderer，也未证明真实数据已被错误归属；它证明的是该文本格式不能唯一反解任意来源结构。

因此不建议靠放宽旧门槛、复制三份摘要或继续写特例解析器推进。建议的最小下一步是保留 Core 已知的结构化来源边界，通过**内部** Worker 请求传递，程序据此提供材料和绑定出处；模型仍只读取／输出文本。相比另造一套可逆文本编码，显式传递现有来源结构更直接，且无需公开 Harness API 或数据库迁移。

这只是通用文本巩固的接口前提，不是效果修复：后续仍须实现不读取问题／答案的自动材料处理、既有记忆更新与去重，并在独立运行环境中经过真实写入、索引、Select、投递、回答对照。不能因为来源可以自动绑定，就宣称语义可靠或准确率已经提升。
